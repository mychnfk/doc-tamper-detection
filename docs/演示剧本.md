# DocGuard 决赛演示剧本

> 面向对象：演示操作者（叙事逻辑）+ 现场执行清单（操作步骤）。评委背景混合（顺丰科技技术领导 + 可能的财务/业务评委），讲解时先说人话结论，追问时再展开技术细节（技术细节见 `docs/QA预案.md`）。
> 四个桥段对应 spec 第 7 节"彩排"清单与第 8 节骨架里点名的核心演示路径。**桥段一数据完整可直接用；桥段二/四依赖评测集真实图片尚未产出，桥段三有机制级真实证据但缺"整图对照"的干净案例**——三处均已标注 `【待填】` 与具体产出方式，不用臆造数字顶替。

---

## 叙事逻辑

按"建立信任 → 展示核心价值 → 展示纠错能力 → 展示不扰民"的顺序讲四个桥段：

1. **重度篡改 → 高分秒判**：CV 和 Agent 结论一致，先证明基础检测是真实有效的。
2. **灰区图 → Loop 放大改判（核心桥段）**：证明 Agent Loop 不是花架子——分数含糊的时候，它真的会多轮查证、改变结论。
3. **误报图 → Agent 排除**：证明 Agent 不是无脑跟着 CV 走，能纠正 CV 的错误判断。
4. **正常图 → 快速通过**：证明系统不会给正常业务添麻烦，不是"逢图必疑"。

## 桥段一：重度篡改 → 高分秒判（数据完整，现在就能用）

**图片**：`example-images/微信圖片_20260629180523_53_237.png`（1080×1330，非切片图）

**真实机跑记录**（`docs/dev-log.md` Task 7 Step 4，最终 prompt 版本）：

| 项目 | 结果 |
|---|---|
| CV 首检 score | 0.9449（远高于当前 `config.HIGH_THRESH=0.7`） |
| Agent 轮数/工具调用 | 3 轮：`zoom_region(region_id=1)` → `zoom_region(region_id=2)` → verdict（VLM 主动收敛，非强制；region_id=1 在 dev-log Task 7 Step 2 首次实测中对应"抬头"区域，Step 3a/4 复跑沿用同一候选框编号未重新逐一描述内容） |
| 结论 | 高度可疑 / 风险：高 |
| basis 是否干净 | 是（无 CV/分数字样泄漏） |
| 耗时 | 1:58.92 |

**操作**：上传该图，选"Agent 复核（推荐）"。可以顺带切到"仅 CV 检测"对比——CV 自己也会给"🔴 高度可疑"（score 0.9449 > 0.7），说明这一档不需要 Agent 介入就能达成共识，用来快速建立"CV 检测本身是真实有效的"第一印象，再引出后面三个桥段展示 Agent 的增量价值（而不是让人以为"篡改都靠 Agent 才能测出来"）。

**注意**：`HIGH_THRESH` 经 Task 10 评测校准后可能变化（当前 0.4/0.7 是决赛升级前的起始值，未经自建集校准）。0.9449 大幅高于当前阈值，校准后大概率仍然秒判成立；如果校准结果有实质变化，彩排时重新确认一次即可，不需要现在假设。

## 桥段二：灰区图 → Loop 放大改判（核心桥段）【待填：评测集产出后】

**现状**：目前有真实 Agent 跑分记录的 3 张图（`53_237.png`/`50_237.jpg`/`check.jpg`）全局分分别是 0.9449 / 0.2536 / 0.2347，没有一张落在 0.4-0.7 灰区（`docs/dev-log.md` Task 7 carry-forward，`eval-images/README.md`"灰区图（决赛关键，务必满足）"小节已经把这件事标记为决赛关键待办）。**这是四个桥段里唯一"不能没有真实图片"的一个**，不能用其他三张顶替，也不能编数字。

**待办**（按 `eval-images/README.md` 灰区图小节执行）：
1. 制作方向：小面积、精改档手法的改动（如印章边缘轻微羽化、单个数字精细 PS）最容易落灰区；改动越大越明显，分数越容易冲出灰区上沿。
2. 用 `scripts/smoke_agent.py` 或 `evaluate.py`（Task 10）实测该图的 CV 首检 score，确认落在 0.4-0.7；不达标就调整改动幅度重做。
3. 用真实 Agent 模式跑一遍，记录：轮数、每轮工具调用（`region_id` 还是手动 `bbox`）、最终 verdict/risk、basis 是否干净、耗时——按桥段一的表格格式补全。

**可预判但需实跑确认的机制**：灰区分数会命中 `agent.py::build_system_prompt` 决策原则第 2 条（"CV 分数处于灰区（{LOW_THRESH}~{HIGH_THRESH}）...优先 investigate 查证"），大概率触发至少一次 `zoom_region` 再 verdict，而不是 1 轮直接通过——但这是代码逻辑推测，不是实测结果，真实轮数/改判方向必须实跑后如实填写，不能假设"一定会改判"。

**产出后动作**：把上表结构套用真实数据替换本节，删除【待填】标记；同步检查 `eval-images/README.md` 灰区图小节是否需要标注"已满足"。

## 桥段三：误报图 → Agent 排除（快速模式 vs Agent 模式对照）

**现状**：目前有一个"机制证明"级别的真实案例，但不是完整的"整图对照"案例，需要如实说明。

**已验证的机制证据**（`docs/dev-log.md` Task 7，`example-images/check.jpg`，3456×4608 切片图）：CV 首检给出候选区域 `region_id=1`（区域均分 0.6328，区域级灰区），Agent 模式放大该区域后核实为"纸张噪点误报"；但同一次复核里 Agent 另外发现了真正的问题（银行账号科学计数法表示 + 无签章），最终整体 verdict 仍是"高度可疑/高"（因为有其它真实问题，不是这个被排除的区域）。轮数/工具调用：2 轮 `zoom_region(region_id=1)` → verdict，耗时 2:07.62（最终 prompt 版本）。这证明"Agent 识别并排除 CV 误报"这个机制是真实工作的，但 `check.jpg` 不是一张"从头到尾都是误报、Agent 一看就说没事"的干净案例。

**两个呈现选项**（彩排时二选一，不臆造数据）：

- **选项 A（现在就能做，零新数据依赖）**：现场演示 `check.jpg`，叙事重点从"误报被排除→整体变正常"调整为"Agent 层层求证、纠正一处 CV 误报、同时抓住了 CV 完全没标出来的真实问题"——这其实是更强的 VLM 复核价值展示（不只是过滤噪音，还能补充 CV 漏掉的语义线索）。彩排时用"快速复核"模式先跑一次并记录输出，再切"Agent 复核"对比查证深度的差异。
- **选项 B（需要评测集产出后才能做）**：等 `eval-images/` 里出现一张"CV 打了中/高分但整图确实是正常单据"的图（可能来自 `normal` 类的自然噪声/水印，或 `amount`/`seal` 类的粗改误标候选），用"快速复核"模式演示标红，再切"Agent 复核"演示放大后排除、改判正常——这是最初设想的干净对照版本。

【待填：彩排前二选一确定；若选 B，需先用 `evaluate.py`/`scripts/smoke_agent.py` 在真实 `eval-images` 素材上跑出候选并记录实测 score/verdict，附具体图片文件名】

**三模式操作提示**：Gradio 左栏"复核模式"是三选一 Radio——"Agent 复核（推荐）"/"快速复核"/"仅 CV 检测"（`app.py::MODE_MAP`），对照演示只需要用同一张图切换这个选项重新点"开始检测"，不需要重启服务或换图。

## 桥段四：正常图 → 快速通过 【待填：评测集产出后】

**现状**：目前 3 张有真实 Agent 跑分记录的图里，没有一张是"clean pass、大家都认为正常"的案例——`53_237.png` 高度可疑，`50_237.jpg`/`check.jpg` 即使 CV 分数低也都被 Agent 判定高度可疑。真正意义上的"正常图快速通过"演示需要 `eval-images/normal/` 的真实业务样张（`eval-images/README.md` 已列：业务组员提供，3-4 张，未修改的真实单据脱敏）到位后才能选定。

**待办**：
1. `eval-images/normal/` 放入脱敏后的真实单据（按 `eval-images/README.md`"数据安全与脱敏"小节要求）。
2. 用 `evaluate.py --mode cv` 或 `scripts/smoke_agent.py` 实测，确认 score 低于 `LOW_THRESH`，且 Agent 模式判定"正常"、轮数少（理想情况 1 轮直接 verdict，不触发 investigate）。
3. 记录耗时——如果是非切片小图，预计比灰区图/高风险图快很多（不需要多轮 zoom）；如果业务样张恰好是切片大图（>1792px），CV 首检本身耗时就不算短（`check.jpg` 的 CV-only 模式实测约 64 秒，`.superpowers/sdd/task-8-report.md`），要如实告知评委"快"是相对 Agent 多轮查证说的，不是说 CV 推理是瞬间完成的。

**备选（临近答辩仍未到位时）**：可以从 `example-images/` 剩余 3 张未实测图（`51_237.jpg`/`54_237.jpg`/`55_237.jpg`）里选一张先用 cv/direct 模式实测，只要能找到一张 CV 分数低、内容也确实找不出问题的，可以临时顶上——但必须先实测出真实数字才能写进剧本，不能假设"应该是正常的"就直接用。

## 现场检查单（彩排/答辩当天，按顺序执行）

1. **`./start.sh` 启动**——脚本会先检查 `.env` 是否存在且含有效 `DASHSCOPE_API_KEY`（正则 `^DASHSCOPE_API_KEY=..+`，空值/注释行/单字符值都会判失败）、TruFor 权重文件是否在位，任何一项缺失会在服务启动前直接报错退出并给出对应提示文字，不会等到 demo 中途才发现（三项前置检查见 `start.sh` 全文）。
2. **等待 warmup 完成**——终端应依次出现三行：`Model loaded (epoch 81)...` → `Warmup done.` → `Running on local URL`（顺序已在 `.superpowers/sdd/task-8-report.md` 的真机验证里确认过）。warmup 用一张 256×256 白图跑一次 `run_single`（`app.py::_warmup()`），意义是把 TruFor 推理路径的首次开销提前消化掉，不落在评委面前的第一次真实请求上。
3. **浏览器打开时带上 `?__theme=light`**（`start.sh` 的 echo 提示会打印这行地址）——虽然 `app.py` 本身已经用 JS 强制移除 dark class（`FORCE_LIGHT`），但 URL 参数是 Gradio 官方文档推荐的、在 JS 执行前就生效的主题指定方式，双保险，避免投影仪在浅色 JS 生效前有一瞬的深色闪烁。
4. **备用 4G 热点**——所有 VLM 调用走 HTTPS 到 DashScope 公网端点（`config.VLM_BASE_URL`），会场 wifi 如果限流/断流，"Agent 复核"和"快速复核"都会受影响；"仅 CV 检测"模式不需要联网。提前确认 4G 热点能正常连到 DashScope（可现场用 `scripts/probe_fc.py` 跑一次验证）。
5. **断网降级预演**——目的是确认"网络/VLM 不可用时 demo 不会卡死或白屏"。已有证据分两层：
   - **单测层面**（随时可重跑 `.venv/bin/python -m pytest tests/test_agent_loop.py -v` 复查）：`test_vlm_exception_falls_back_to_cv` 用 `ConnectionError`（网络异常最常见的异常类型）模拟 VLM 不可达，断言最终仍会得到 CV-only 的 verdict 而不是抛出异常；`test_direct_dead_yields_fallback_notice_then_cv` 验证"快速复核"模式自身失败时也会先给出 `⚠️ 已切换复核方式` 提示气泡而不是静默或崩溃。
   - **真机层面**（`.superpowers/sdd/task-8-report.md`）：曾用等效故障模式做过真实验证——故意改错 `.env` 里的 `DASHSCOPE_API_KEY`，效果与断网一致（`call_vlm` 都是"这次请求发不出去/拿不到合法响应"），UI 上观察到 `⚠️ 已切换复核方式` 气泡 + 折叠的技术详情 + 最终 CV-only 判定卡片，服务进程本身没有崩溃。
   - **尚未做过的**：没有用"真实拔网线/关热点"的方式复测过（只测过错误 API key 这个等效故障，两者触发的异常类型不一定完全相同）。**建议彩排时至少做一次真实断网**（关掉电脑 wifi 或热点），在 Agent 模式下跑一张图，确认表现和上面两条证据一致；如果发现不一致（比如 DNS 超时的异常类型导致某处窄捕获漏网），现在改还来得及，好过在评委面前才发现。
